By the end of this lesson you will be able to spot a transitive dependency and move the dependent column to its own table to reach 3NF.

The Third Normal Form (3NF) builds on First Normal Form (1NF) and Second Normal Form (2NF). It helps eliminate data redundancy and improves data integrity in relational databases.

To achieve 3NF, the following conditions must be met:

1. The table must be in 2NF.
2. There should be no **transitive dependencies**: a non-key column must not depend on another non-key column.

In other words, every column should describe the key, not some other column.

By eliminating transitive dependencies, 3NF helps prevent update, insertion and deletion anomalies.

---

## Example

Suppose we have a table called "Students" with the columns Student_ID, Student_Name, Tutor_ID and Tutor_Room:

| Student_ID | Student_Name | Tutor_ID | Tutor_Room |
|------------|--------------|----------|------------|
| 1          | Alice        | T1       | Lab 3      |
| 2          | Bob          | T2       | Room 12    |
| 3          | Charlie      | T1       | Lab 3      |
| 4          | Dana         | T1       | Lab 3      |
{:class="table table-single"}

The primary key is Student_ID. Tutor_ID depends on the student, which is fine. But Tutor_Room depends on Tutor_ID, not on the student. That's a transitive dependency: Student_ID → Tutor_ID → Tutor_Room.

This causes problems:

- **Update anomaly:** if tutor T1 moves room, we must change three rows, and if we miss one the data contradicts itself
- **Insertion anomaly:** we can't record a new tutor's room until they have a student
- **Deletion anomaly:** if Bob leaves, we lose the fact that T2 is in Room 12

To normalise to 3NF, move the tutor details into their own table:

### Table: Students

| Student_ID | Student_Name | Tutor_ID |
|------------|--------------|----------|
| 1          | Alice        | T1       |
| 2          | Bob          | T2       |
| 3          | Charlie      | T1       |
| 4          | Dana         | T1       |
{:class="table table-single"}

### Table: Tutors

| Tutor_ID | Tutor_Room |
|----------|------------|
| T1       | Lab 3      |
| T2       | Room 12    |
{:class="table table-single"}

Now each tutor's room is stored once. Moving a tutor means changing one row, and a tutor can exist without any students. You can still get the original view back with a `JOIN`.

## See it in SQLite

Run this complete program. It builds the 3NF tables from the example, then changes a tutor's room:

```python
import sqlite3

connection = sqlite3.connect(":memory:")
connection.executescript("""
    CREATE TABLE tutors (tutor_id TEXT PRIMARY KEY, tutor_room TEXT);
    CREATE TABLE students (
        student_id INTEGER PRIMARY KEY,
        student_name TEXT,
        tutor_id TEXT REFERENCES tutors(tutor_id)
    );
    INSERT INTO tutors VALUES ('T1', 'Lab 3'), ('T2', 'Room 12');
    INSERT INTO students VALUES (1, 'Alice', 'T1'), (2, 'Bob', 'T2'), (3, 'Charlie', 'T1'), (4, 'Dana', 'T1');
""")

with connection:
    cursor = connection.execute("UPDATE tutors SET tutor_room = ? WHERE tutor_id = ?", ("Lab 5", "T1"))
print("Rows changed:", cursor.rowcount)

query = """
    SELECT s.student_name, t.tutor_room
    FROM students AS s JOIN tutors AS t ON t.tutor_id = s.tutor_id
"""
for row in connection.execute(query):
    print(row)
```

One row changes (`Rows changed: 1`), yet Alice, Charlie and Dana all show `Lab 5` through the join. In the original single table it would have been three rows to change.

2. Delete Bob and check that tutor `T2` and their room are still stored.
3. Which column is the transitive dependency in this table: `Employee_ID, Employee_Name, Department_ID, Department_Name`?

## Common Issues

- **Problem**: A `JOIN` returns fewer rows than you expect after splitting a table.
- **Solution**: Check every `tutor_id` in `students` exists in `tutors`, and use `LEFT JOIN` if some may not.
- **Why**: An inner join drops rows with no match.
